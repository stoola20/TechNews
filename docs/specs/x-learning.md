# X 收藏與技術學習工具

**Status:** ready-for-agent

**使用者:** 單一使用者，自用。

## Problem Statement

使用者在 X 收藏或分享值得學習的英文技術內容，但主貼文、作者補充、引用、圖片、影片與外部文章分散，難以整理成可反覆閱讀、搜尋與追問的繁中教材。

現有技術部落格 digest 可生成 Telegram 導讀，但沒有 X 書籤同步、完整媒體理解或與 Worker 資料連接的文章庫。訊息長度限制與相關性篩選不適合使用者主動選中的收藏。

## Solution

使用者透過 Telegram 分享連結，或在 X 加入書籤。系統將每個已接收的來源保存為工作，取得可用證據，再使用 Gemini 解析媒體及編寫完整繁中教材。

教材保存在私人手機網頁文章庫，提供關鍵字搜尋、已讀狀態、筆記與單篇／跨文章來源追問。Telegram 傳送導讀與完整文章連結，不限制教材篇幅，也不限制通知篇數。

主文無法取得時保留待重試。其他證據缺漏時，可以生成已確認內容，但必須醒目標示缺漏與未確認事項，不能猜測補齊。月預算為 US$30；達門檻後保留工作並停止新增付費呼叫，等待使用者手動恢復。

## User Stories

1. 身為使用者，我希望把 X 連結分享給 Telegram bot，以便將想學的內容加入文章庫。
2. 身為使用者，我希望分享外部技術文章連結，以便用同一套流程學習。
3. 身為使用者，我希望系統確認已收到連結，以便知道工作已保存。
4. 身為使用者，我希望重複分享同一來源不重複付費生成，以便避免重複文章與支出。
5. 身為使用者，我希望連接自己的 X 帳號，以便使用私人書籤入口。
6. 身為使用者，我希望每天同步書籤，以便不用再次分享已收藏的內容。
7. 身為使用者，我希望第一次連接時預覽可取得的既有書籤與估算，以便決定是否回補。
8. 身為使用者，我希望既有書籤等待我啟動回補，以便掌握首次處理量。
9. 身為使用者，我希望啟用後的新書籤自動整理，以便日常收藏能進入學習流程。
10. 身為使用者，我希望看到分頁與同步尚未完成的狀態，以便知道哪些收藏還沒取得。
11. 身為使用者，我希望被預算中斷的同步能續跑，以便不必從頭付費取得所有資料。
12. 身為使用者，我希望所有已接收的收藏都整理，以便不被系統以低相關性丟棄。
13. 身為使用者，我希望取得完整長文與主貼文，以便不只閱讀摘要或截斷內容。
14. 身為使用者，我希望包含父貼文與引用上下文，以便理解作者在回應什麼。
15. 身為使用者，我希望包含同串作者續寫與補充，以便保留操作條件與限制。
16. 身為使用者，我希望作者補充和其他人的留言分開，以便不混淆主張來源。
17. 身為使用者，我希望直接外連文章也成為證據，以便理解貼文所指的完整技術內容。
18. 身為使用者，我希望重要討論串在 24–48 小時內重查一次，以便補上較晚新增的作者資訊。
19. 身為使用者，我希望系統理解圖片中的圖表、程式與操作畫面，以便教材不只解釋圖片替代文字。
20. 身為使用者，我希望系統理解影片的畫面與聲音，以便操作示範能被整理成可應用的教材。
21. 身為使用者，我希望教材保留媒體時間點，以便回到原影片查核。
22. 身為使用者，我希望超過 20 分鐘或 200 MB 的影片被保留並提示，以便自行決定後續處理，而非被截短。
23. 身為使用者，我希望主文取得失敗時保留工作，以便恢復可用後再處理。
24. 身為使用者，我希望部分媒體或補充缺漏時仍能讀到已確認內容，以便不必無限等待。
25. 身為使用者，我希望缺漏醒目顯示，以便不誤認為教材已涵蓋所有來源。
26. 身為使用者，我希望重試後能補齊同一篇文章，以便不用整理多份重複教材。
27. 身為使用者，我希望教材使用繁體中文與台灣用語，以便直接閱讀與應用。
28. 身為使用者，我希望保留原文的目的、背景、機制、推理、例子、操作與限制，以便學到完整概念。
29. 身為使用者，我希望術語、人名、程式碼與數字忠於來源，以便避免翻譯造成技術錯誤。
30. 身為使用者，我希望原作者主張與補充教學例子分開，以便辨認證據和解釋。
31. 身為使用者，我希望不因我的 iOS 背景而自動加入類比，以便教材直接解釋原本技術。
32. 身為使用者，我希望分享文章完成後收到 Telegram 通知，以便立即知道可以閱讀。
33. 身為使用者，我希望書籤文章集中收到 Telegram 通知，以便減少分散的通知。
34. 身為使用者，我希望當日所有完成的文章都出現在通知中，以便不受 3–5 篇的顯示建議限制。
35. 身為使用者，我希望超長通知自動分批，以便不遺漏文章連結。
36. 身為使用者，我希望通知失敗能重送已保存結果，以便不用重新生成教材。
37. 身為使用者，我希望手機可以登入私人文章庫，以便隨時閱讀而不公開收藏。
38. 身為使用者，我希望文章庫顯示完整文章與來源，以便通知只是入口。
39. 身為使用者，我希望用關鍵字搜尋標題、文章與已保存來源，以便找回曾讀過的內容。
40. 身為使用者，我希望標記已讀並保存筆記，以便管理自己的學習狀態。
41. 身為使用者，我希望對單篇文章追問，以便釐清機制與操作。
42. 身為使用者，我希望跨文章追問，以便比較不同工具或觀點。
43. 身為使用者，我希望追問回答附上可查核來源，以便回到原文與媒體證據。
44. 身為使用者，我希望證據不足時明確說明無法確認，以便不把模型推測當事實。
45. 身為使用者，我希望看到月費估算與剩餘預算，以便掌握支出。
46. 身為使用者，我希望初次書籤預覽的 X 費用也計入預算，以便估算不忽略收集成本。
47. 身為使用者，我希望達到預算門檻就暫停新增付費工作，以便控制費用。
48. 身為使用者，我希望暫停後仍能收件、閱讀與查看待處理內容，以便不丟掉收藏。
49. 身為使用者，我希望我手動恢復後才繼續付費工作，以便下月也不擅自解除暫停。
50. 身為使用者，我希望持續保存原文、文章、筆記與解析結果，以便日後回頭查。
51. 身為使用者，我希望原始媒體先保留 30 天，以便重查近期內容並控制儲存量。
52. 身為使用者，我希望既有部落格 digest 繼續運作，以便新工具不破壞現有用途。

## Implementation Decisions

### 系統與模型

- 沿用 Cloudflare Worker，新增獨立的收藏學習子流程。使用 D1 保存來源、教材、任務、閱讀與費用紀錄；使用 R2 保存媒體。
- 以 Gemini 3.8 Flash 作為第一版解析、寫作與追問的起始模型。保留模型名稱設定，但不新增 Claude、OpenAI、Jev 或向量服務依賴。
- Gemini 接收取得的文字與原生圖片／影片素材，輸出完整教材、來源引用與媒體時間點觀察。解析與寫作是邏輯階段，不要求兩家模型，也不要求每篇兩次生成。
- 不以 Telegram 長度限制裁切教材。超過模型可處理範圍時，保留來源與待處理狀態，不默默截斷原文。
- 背景任務保存於 D1，Cloudflare Queues 負責喚醒與失敗重送。日次排程也檢查未完成工作，避免訊息到期或漏送造成資料遺失。

### 收件、同步與去重

- 私人網頁與 Telegram 收件都接受連結。Telegram webhook 驗證 secret header 與允許的使用者／chat，避免外人使用 bot 消耗預算。
- 以正規化來源 URL 或 X post ID 去重；同一來源經分享與書籤進入時，保存兩種收件關係並重用同一篇教材。
- X 使用 OAuth 2.0 PKCE，取得書籤、貼文與使用者必要讀取權限，以及 refresh token 所需權限。授權狀態與回呼需驗證；token 不出現在 URL、文章、紀錄或前端回應。
- 每日台灣時間 09:00 啟動書籤同步，分頁保存 checkpoint。不能把發文 ID 當成收藏時間，也不能以遇到已知 ID 為充分停止條件。
- 首次同步建立既有書籤待確認清單；預覽本身會產生 X 讀取費。未掃完時只顯示已取得數量，不宣稱它是全部書籤總數。
- 使用者啟動回補後才處理既有清單；完成首次基線後發現的新書籤直接排入處理。初次掃描尚未完成時，收藏新舊無法可靠區分，介面必須標示此狀態，不能丟棄未分類項目。
- 書籤 API 的資料可能在分頁期間改變，定期從頭核對並以來源身份去重；不能承諾取得來源平台已刪除或不再提供的內容。

### 證據與媒體

- 取得主文、長文、父貼文、引用、同串作者補充與直接外連文章。作者補充分頁受費用與來源能力限制，未完成時保留進度與缺漏狀態。
- 不巡邏所有他人留言，不遞迴追蹤外部文章的所有連結。已取得的他人引用或父貼文以獨立作者來源保存。
- 重要討論串先定義為需要作者補充查核的 X 討論串，預設在取得後 24 小時重查一次。新增來源補充後更新同一篇文章與缺漏狀態，不重複建立文章。
- 相容 X 官方文件目前出現的兩種回應欄位命名。出站參數以供應商契約設定與少量真實呼叫確認，不把文件差異當作已驗證的 API 行為。
- 圖片與影片保存下載狀態、來源 URL、媒體類型、大小、長度及原始來源關係。影片預覽圖片不能當作完整影片證據。
- 單支影片上限為 20 分鐘、200 MB；超限保留並提示，不截短。媒體以串流保存及上傳，避免把整段影片載入 Worker 記憶體。
- Gemini Files 是暫時的處理存放位置，不能取代自己的來源保存。保存處理所需的檔案參照、到期與狀態；到期後從保留中的原始媒體重新準備。
- 主文無法取得時不生成教材，保留待重試。媒體、作者補充或外連缺漏時，可生成已取得內容，但文章與列表要明確顯示缺漏，重試後補齊。
- 超限影片與需重新授權的來源保留待人工處理狀態，不能不斷重試同一不可恢復條件。
- 原文、文章、筆記與解析結果持續保存；原始媒體保留 30 天。媒體到期後保留其解析結果與原始連結，標示原始檔已到期；再次取得視為新的取得工作。

### 私人文章庫與追問

- 文章庫以現有 RUN_TOKEN 登入，使用受保護 session。通知連結不得包含 RUN_TOKEN 或其他金鑰。
- 未登入者無法取得文章、來源、筆記、搜尋與追問結果。登入後可使用文章列表、完整閱讀頁、缺漏／處理狀態、已讀狀態與筆記。
- 第一版採關鍵字搜尋，不引入 embedding、向量資料庫或另一個 Python 後端。跨文章追問從已保存內容選取相關片段，提供可查核來源。
- 單篇追問限定該篇及其來源；跨文章追問可使用文章庫相關來源。回答只能引用實際提供的來源 ID，媒體主張需對應取得的時間點或畫面證據。
- 沒有足夠來源時，回答明確說明無法確認。來源內容一律視為資料，不執行其中要求更改系統、取得秘密或發送訊息的指令。

### 通知與排程

- 所有通知透過 Telegram。分享來源完成後逐篇通知，書籤來源按本次日次處理集中通知；晚完成的文章在下一批納入。
- 每篇通知提供導讀、文章連結與必要缺漏提示。沒有完成文章時不發空的文章清單。
- 所有完成文章都納入，無 3–5 篇限制。長通知分批，每批內容與發送狀態持續保存，失敗時重用既有教材。
- Telegram 發送與資料庫更新不是同一交易；若發送成功但回應遺失，重送仍可能出現少量重複通知，不能宣稱 exactly-once。

### 預算與持續保存

- 新流程的月預算為 US$30，先預留 Cloudflare 基本費 US$5。X、Gemini、儲存與相關新流程用量由剩餘預算控管；既有部落格 digest 費用另計。
- 付費呼叫前以保守估算預留成本；成功後依資源與 token 用量結算。尚未確定是否計費的失敗仍保留預留，不能因回應失敗將用量歸零。
- 預算統計以台灣曆月呈現；供應商可能採不同計費週期與去重時間。畫面清楚標示估算、已預留與未知用量，並保留價格設定的查核依據。
- 達門檻後停止新付費工作，包含 X 同步、Gemini 生成、付費重試與追問。未取得的書籤顯示同步未完成；已收到的分享仍可排隊。
- 暫停狀態持續保存，跨月也不自動恢復。使用者手動恢復時重新檢查可用預算；若仍不足，繼續保留工作並提示。
- 估算不能保證供應商帳單的精確硬上限；保存可核對的用量與操作紀錄，並提供供應商端 spending limit 的設定說明。

## Testing Decisions

- 主要測試邊界已由使用者確認：收件／書籤 → 真實資料表與 migration → 任務處理 → 文章庫閱讀與來源追問。
- 測試外部可見行為，不以私有 helper 呼叫次數或內部實作細節當作成功條件。使用既有 Worker pipeline 測試作為先例，以記憶體 SQLite 執行真實 schema，替換外部網路回應。
- 收件驗證：網址正規化、分享與書籤去重、重複 webhook、私密入口授權、非法來源不觸發付費或內網讀取。
- 同步驗證：完整分頁、首次基線、既有回補、新收藏、已知 ID 不能提前截斷、授權刷新、費用中斷與續跑、來源平台資料變動。
- 證據驗證：長文不截斷、引用與父貼文、作者補充、直接外連、來源缺漏與重試後補齊；影片不能只用預覽圖替代。
- 媒體驗證：串流大小上限、長度上限、Gemini Files 處理中／完成／失敗／到期、原生影片輸入、媒體時間點、到期保存政策。
- 教材驗證：生成完整文章，保留來源尾端與限制；不受 Telegram 長度裁切；不自動丟棄手動收藏；模型拒絕或輸出未完成時不保存為完整教材。
- 預算驗證：同時工作不超額分配可用預算、API 成功與不確定失敗的紀錄、低預算停止讀取與生成、暫停不丟工作、月切換不自動恢復、手動恢復仍檢查剩餘預算。
- 通知驗證：分享逐篇、書籤集中、無篇數限制、長通知分批、發送失敗不重新生成、晚完成文章不漏送。
- 文章庫驗證：登入保護、搜尋、已讀、筆記、單篇與跨文章問答；不存在的來源 ID 不成為有效引用，證據不足時清楚說明。
- 保留少量供應商契約測試，檢查請求形狀與回應驗證。少量真實 API 驗證另存證據，確認 X 欄位、分頁、長文、媒體取得與 Gemini 原生影片處理。
- 既有 digest 回歸測試必須通過。打包檢查與本機操作驗證完成後，再整理外部設定；尚未具備憑證的真實驗證必須明確列為未完成。

## Out of Scope

- 完整 iOS App、Share Extension、離線 App 同步。
- 公開作者巡邏、主題巡邏、For You 瀏覽與登入瀏覽器自動化。
- Claude、OpenAI、Jev、本機模型或新向量服務的正式串接。
- 多使用者、公開分享、付費訂閱與團隊權限。
- 不受限制的影片處理、任意附件收件、全網遞迴爬取與巡邏所有留言。
- 把供應商文件列出的能力或模擬測試視為已通過真實素材驗收。

## Further Notes

所有選文入口反映使用者主動選擇，不採自動低分刪除或略過。費用限制控制工作何時執行，不決定哪些收藏值得整理。

X 書籤同步沒有 `since_id`，且目前官方文件未保證排序與全部歷史範圍。完整度應以取得紀錄與未完成狀態呈現。API 權限、刪除來源與媒體失效仍可能阻止取得；不能承諾平台不再提供的內容。

Gemini 的原生影片輸入也會取樣，不能保證看見每一幀。關鍵操作與時間點需用真實素材驗證。
