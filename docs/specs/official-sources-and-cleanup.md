# 官方來源紀錄、X 費用帳本與架構整理

**Status:** ready-for-agent

**使用者：** 單一使用者，自用。需求已逐題確認。tickets 依本規格拆分後直接開發，全部在同一個分支完成，最後開一個 PR 到 develop；部署由使用者執行。

## Problem Statement

使用者用這個工具收取技術新知，主要透過 Telegram 通知與私人文章庫。目前有五個問題。

1. **兩代官方流程並存，互相干擾。** 舊的每日導讀流程（四選一摘要模型、手機設定頁、`/run`、`/preview`）與文章庫流程共用同一份「來源看過哪些網址」的紀錄，但兩邊對「看過」的定義不同：舊流程記「已處理」，文章庫記「已收件」。改由文章庫接手官方來源後，舊流程沒處理完的積壓被當成新文章一次收件、推送，其中包含發表將近一年的舊文。使用者只想收新知。此外，文章庫啟用時，`/run` 仍會走舊流程，用舊模型發出導讀。
2. **出事時看不到原因。** 管理頁沒有官方來源的資訊：最後檢查時間、這輪找到幾篇、收了幾篇、為什麼略過、哪個來源失敗。「看過的網址」存成一個會滾動截斷的 JSON 陣列，看不出某篇何時、為什麼被收或被略過。排查只能直接查正式資料庫。來源壞掉時（網站改版、被擋），使用者只會覺得「最近文章變少」。
3. **X 費用帳本有不會消失的「未確認」金額。** 每次呼叫 X 前，程式先預留最壞情況的費用；呼叫失敗時，整筆預留記成「未確認」，並一直算進月預算。另有一種「重讀風險」估算也記成未確認。管理頁沒有作廢或刪除的入口。使用者找不到處理方式而按了「手動恢復」，但這個按鈕做的是解除暫停、重新排隊，跟費用無關。
4. **分類要等巡邏。** 文章完成後，要等每 5 分鐘一次的維護排程才會分類，所以 Telegram 通知裡沒有主題。同一個維護排程每次還會重跑早就完成的一次性舊資料搬移。
5. **不再使用的程式擴大了閱讀與維護範圍。** 另一套 Python RAG 問答服務與文章庫不共用資料，已不再使用。程式碼多處把整個函式寫成一行，diff 難以審查。部分測試把寫死的日期拿來和真實時間比較，時間一過就會自己失敗。

## Solution

移除舊的每日導讀流程，官方來源只走文章庫這一條路。官方來源只收 7 天內發表的文章。

管理頁新增「官方來源」區塊，原本在手機設定頁的「想收到的內容」與來源清單也併進來。每個來源一列，顯示開關、最後檢查時間、最近一輪的找到／收件／太舊略過篇數，以及失敗原因。點開來源可以看最近 7 天每篇的處理結果；太舊略過的文章可以按「仍要收件」。紀錄保留 30 天。同一個來源連續兩天 08:00 都失敗時，發一則 Telegram 提醒。

文章完成後立刻分類，Telegram 通知第一行附上主題。

X 呼叫有回應、但回的是錯誤時，記 $0；只有完全沒回應時才記未確認。管理頁可以逐筆作廢未確認費用，既有的未確認費用在升級時全部作廢。不再估算重讀風險。預算區塊列出本月 X 失敗呼叫的次數與明細。「手動恢復」改成只在暫停時出現，並說明暫停原因與按下的效果。

最後移除 Python RAG，讓測試可以指定「現在時間」，並用 formatter 一次性重排程式碼。

## User Stories

### 官方來源與新鮮度

1. 身為使用者，我希望官方來源只收發表 7 天內的文章，以便 Telegram 只收到新知。
2. 身為使用者，我希望來源列表突然冒出的舊文章（RSS 一次放出更多歷史、流程交接留下的積壓）不會被收件或通知，以便不被舊聞洗版。
3. 身為使用者，我希望列表上沒有日期的文章在抓到原文後再檢查一次發表時間，以便部落格類來源也遵守 7 天期限。
4. 身為使用者，我希望 7 天期限從收件時間起算，以便 Mac 離線等處理延誤不會讓新文章被當成舊文丟掉。
5. 身為使用者，我希望自己分享或收藏的文章不受 7 天期限限制，以便主動挑的文章一定會整理。
6. 身為使用者，我希望新來源第一次執行時只回補 7 天內的文章，以便新增來源時不會湧入舊文。

### 管理頁：官方來源區塊

7. 身為使用者，我希望在管理頁看到每個官方來源各一列，以便一眼看出各來源的狀況。
8. 身為使用者，我希望每列顯示最後檢查時間，以便知道排程有沒有跑。
9. 身為使用者，我希望每列顯示最近一輪找到、收件、太舊略過的篇數，以便判斷收件量是否正常。
10. 身為使用者，我希望來源失敗時，那一列顯示失敗原因，以便知道是網站改版、被擋還是暫時錯誤。
11. 身為使用者，我希望點開來源後，能看到最近 7 天每篇文章的處理結果（標題、發表日、收件／太舊略過／初次基準），以便查出某篇為什麼被收或沒被收。
12. 身為使用者，我希望收件的文章連到文章庫裡的那一篇，以便直接去讀。
13. 身為使用者，我希望明細裡的標題連到原文，以便判斷被略過的文章值不值得看。
14. 身為使用者，我希望太舊略過的文章旁有「仍要收件」按鈕，以便一鍵收進文章庫整理。
15. 身為使用者，我希望「仍要收件」的效果等同我主動分享（不受主題篩選，完成後照常通知），以便行為可以預期。
16. 身為使用者，我希望來源紀錄保留 30 天，以便回頭查最近一個月的狀況，又不讓資料無限增加。
17. 身為使用者，我希望區塊標題註明「只收 7 天內發表的文章」，以便記得目前的規則。

### 管理頁：來源與主題設定

18. 身為使用者，我希望「想收到的內容」文字框放在官方來源區塊上方，以便在同一個地方調整篩選條件。
19. 身為使用者，我希望每個來源都有開關，以便暫停某個來源而不必刪除設定。
20. 身為使用者，我希望關閉的來源保留歷史紀錄並標示「已關閉」，以便重新開啟時知道過去的狀況。
21. 身為使用者，我希望新增或修改來源網址的功能收在「進階：編輯來源 JSON」裡，以便日常操作不被進階設定干擾。
22. 身為使用者，我希望設定儲存後在下一輪排程生效、不需要重新部署，以便在手機上就能調整。
23. 身為使用者，我希望來源設定格式錯誤時看到明確的錯誤、原設定保持不變，以便不會因為打錯字讓所有來源停擺。

### 來源失敗提醒

24. 身為使用者，我希望同一個官方來源連續兩天 08:00 都失敗時收到一則 Telegram 提醒，以便及早發現來源壞掉。
25. 身為使用者，我希望提醒寫出來源名稱和失敗原因，並指向管理頁，以便知道要去哪裡看。
26. 身為使用者，我希望同一次故障在恢復前只提醒一次，以便不被重複訊息打擾。
27. 身為使用者，我希望來源恢復時不另外發通知，以便訊息只在需要我處理時出現。
28. 身為使用者，我希望「列表抓不到任何文章」也算失敗，以便網站改版造成的空白列表會被發現。
29. 身為使用者，我希望關閉的來源不會觸發失敗提醒，以便暫停來源時不收到誤報。

### 分類與通知

30. 身為使用者，我希望文章完成後立刻分類，以便打開文章庫時主題已經在了。
31. 身為使用者，我希望 Telegram 通知第一行附上主題標籤，以便在 Telegram 就能判斷要不要讀。
32. 身為使用者，我希望分類失敗時通知照常發出、只是不附主題，以便分類問題不會擋住新知。
33. 身為使用者，我希望分類失敗後自動重試，以便暫時錯誤不會讓文章永遠沒有主題。
34. 身為使用者，我希望手動設定的主題仍然不會被自動分類覆寫，以便我的判斷優先。
35. 身為使用者，我希望管理頁的「重新分類全部」照常可用，以便調整主題表後重新整理。
36. 身為使用者，我希望文章更新通知（【更新】）也附上主題，以便兩種通知格式一致。

### X 費用帳本

37. 身為使用者，我希望 X 回錯誤（例如 429、503、401）時，那次呼叫記 $0，以便沒讀到資料的呼叫不吃掉預算。
38. 身為使用者，我希望只有 X 完全沒回應（逾時、連線中斷）時才記成未確認，以便只有真的無法判斷的情況需要我處理。
39. 身為使用者，我希望管理頁每筆未確認費用旁都有「作廢」按鈕並可填說明，以便核對 X 後台後自己處理。
40. 身為使用者，我希望作廢的費用不算進月預算，但仍列在「已作廢」明細並顯示說明，以便日後對帳。
41. 身為使用者，我希望既有的 X 未確認費用（失敗預留與重讀風險估算）在升級時全部標為作廢，以便預算立刻反映實際花費。
42. 身為使用者，我希望不再記錄重讀風險估算，以便帳本只留下實際讀取的費用。
43. 身為使用者，我希望預算區塊顯示「X 失敗呼叫：本月 N 次，未計費」，以及最近一次的狀態碼與發生情境（例如書籤同步），以便錯誤不會因為記 $0 而被忽略。
44. 身為使用者，我希望點開 X 失敗呼叫能看到每次的時間、讀取類型與狀態碼，以便判斷是額度、權限還是 X 本身的問題。

### 暫停與恢復

45. 身為使用者，我希望「恢復處理」按鈕只在暫停時出現，以便不會在沒暫停時誤按。
46. 身為使用者，我希望暫停時看到暫停原因（手動或費用不足），以便知道恢復前要先處理什麼。
47. 身為使用者，我希望按鈕旁用一句話說明按下會做什麼（解除暫停、把暫停中的文章重新排隊、續跑書籤同步），以便知道它不會處理費用。
48. 身為使用者，我希望費用不足而無法恢復時，看到「剩餘預算為 0，請先作廢未確認費用或調整月預算」，以便知道下一步。

### 移除舊流程

49. 身為使用者，我希望舊每日導讀的頁面與端點（手機設定頁、`/config`、`/run`、`/preview`）移除並回 404，以便只剩一條官方流程。
50. 身為使用者，我希望文章庫裡既有的舊版短導讀保持原樣，可讀、可搜尋，筆記與已讀紀錄都保留，以便不失去過去的資料。
51. 身為使用者，我希望 README 的快速開始改以文章庫為準，以便文件與實際功能一致。
52. 身為使用者，我希望部署時不再需要 OpenAI、Anthropic 金鑰與摘要模型設定，以便部署設定更少。
53. 身為使用者，我希望 `/health` 照常可用，以便確認服務是否在線。

### 維護與程式整理

54. 身為使用者，我希望 5 分鐘一次的維護排程只做需要定期做的事，以便減少不必要的資料庫讀取。
55. 身為使用者，我希望一次性的舊資料搬移仍可從管理頁「維運」按鈕手動執行，以便需要時能重跑。
56. 身為使用者，我希望 Python RAG 問答服務從 repo 移除，以便專案只留下實際使用的部分；需要時可以從 git 歷史找回。
57. 身為使用者，我希望測試不會因為真實時間經過而自己失敗，以便測試結果可信。
58. 身為使用者（也是審查者），我希望程式碼經過 formatter 統一排版，以便 diff 容易審查。
59. 身為使用者（也是審查者），我希望排版 commit 不會蓋掉 `git blame` 的歷史，以便追查某行程式的來由。

## Implementation Decisions

### 官方流程只留文章庫

- 移除舊每日導讀：digest 執行、單篇導讀處理、四選一摘要模型（Workers AI 的 Gemma 4 與 Nemotron 3、OpenAI、Anthropic）、手機設定頁、`/config`、`/run`、`/preview`。移除後這些路徑回 404，與其他未授權路徑一致。
- 移除 `LEARNING_ENABLED` 開關，Worker 一律啟用文章庫；08:00 排程只做文章庫的官方發現。
- 移除不再使用的部署變數 `MODEL_PROFILE`、`MAX_ARTICLES_PER_RUN`；程式不再讀取 `OPENAI_API_KEY`、`ANTHROPIC_API_KEY`。Workers AI binding 保留給主題分類，Browser Run binding 保留給官方擷取備援。
- D1 `settings` 的 `digest` 設定改成只含 `interests` 與 `sources`；讀到舊格式時忽略 `model_profile`，下次儲存時移除。
- 舊 `articles` 表保留，不刪除，程式不再寫入；只有管理頁「維運」的手動搬移會讀取它。
- 文章庫裡 `edition='legacy_digest'` 的文章維持原樣。

### 新鮮度期限

- 部署變數 `MAX_ARTICLE_AGE_DAYS`（預設 7，至少 1）是官方來源唯一的期限設定：新來源首次回補、每日發現，以及抓到原文後的檢查，都用這個值。
- 發現時：列表上有日期、而且早於「現在減 N 天」的條目，記為太舊略過，不收件。
- 抓到原文後：只來自官方收件、尚未通知過、也不是舊版短導讀的文章，以官方收件時間減 N 天為基準。發表時間早於基準時，文章狀態設為 `filtered` 並寫入原因，不呼叫文字模型、不通知。
- 分享、收藏與「仍要收件」的文章不受期限限制。
- 日期解析沿用文章庫現有的發表時間正規化規則；無法解析的日期視為「沒有日期」，不判定為太舊。

### 來源看過紀錄：一個網址一列

- 新表 `source_entries` 取代 `source_state.seen_urls_json`，以「來源＋網址」為主鍵，欄位如下：
  - 首次看到時間、最後出現在列表的時間。
  - 列表提供的標題與發表時間。
  - 決策：`baseline` 初次基準、`collected` 收件、`stale` 太舊略過。
  - 決策原因、對應的文章 id、是否由使用者手動收件。
- 發現流程用這張表判斷是否看過。migration 把既有 seen 清單轉成 `baseline` 條目（沒有標題與日期）。
- `source_state` 只保留來源層級的資料：初始化時間與最後成功檢查時間。
- 抓到原文後才判定太舊的文章，對應條目也更新為 `stale` 並寫入原因。
- 保留期限：條目在 30 天內都沒有再出現在來源列表時，由維護排程刪除。仍在列表上的網址不刪，避免舊網址被當成沒看過。

### 每輪發現紀錄

- 新表 `source_runs`：每次官方發現，每個啟用中的來源各寫一列，記錄執行時間、找到數、收件數、太舊略過數、初次基準數、成功或失敗、失敗原因。超過 30 天的紀錄由維護排程刪除。
- 「列表抓不到任何文章」記為失敗。
- 連續失敗：從同一來源的執行紀錄往回數連續失敗次數，成功一次就中斷。剛好第二次失敗時建立一則提醒；第三次以後不重發，恢復後再故障重新從一開始計。不在 `source_state` 另存計數，新來源首次就失敗時也不會因此跳過初次基準。關閉的來源不發現、不計次數。
- 提醒內容：來源名稱、最近一次失敗原因、管理頁連結。走既有的通知保存與送出機制（保存內容，失敗只重送同一份），但類型與文章通知分開，不影響文章通知的去重。

### 管理頁「官方來源」區塊與 API

- 區塊標題註明目前的期限（「只收 N 天內發表的文章」），上方是「想收到的內容」文字框，下面每個來源一列：
  - 開關、名稱、最後檢查時間、最近一輪的找到／收件／太舊略過數。
  - 狀態：正常、失敗（含原因）、已關閉。
- 點開來源顯示最近 7 天首次看到的條目：發表日、標題（連到原文）、決策；收件的連到文章庫的那一篇，太舊略過的附「仍要收件」按鈕。
- 收合的「進階：編輯來源 JSON」可以新增、修改、刪除來源，驗證規則沿用現有的來源設定驗證。
- 來源設定的每一筆新增 `enabled`（預設 true）。關閉的來源不參與發現，紀錄保留。
- API（都需要管理頁登入）：
  - 讀取官方來源：回傳期限天數、想收到的內容、每個來源的設定、最近一輪結果、狀態與最近 7 天條目。
  - 儲存設定：同時接收想收到的內容與來源清單，驗證失敗時回 400，原設定不變；開關也透過這個 API 儲存。
  - 仍要收件：接收來源 id 與網址。以 `web` 入口收件（等同主動分享），條目決策改為 `collected` 並標記為手動收件。

### 分類時機與通知主題

- 文章寫成 `ready` 或 `partial` 後，同一個處理流程立刻呼叫分類，再建立通知。這適用於 Gemini 寫作，也適用於 Mac 執行器回報完成。分類仍用 Workers AI Gemma 4，提示詞、輸出驗證、手動主題優先的規則都不變。
- 分類失敗沿用現有的失敗次數與延後重試欄位；通知不等待，照常建立、不附主題。
- 維護排程的分類步驟保留，只會處理重試到期的文章、「重新分類全部」排入的文章，以及尚未分類的既有文章。
- 通知第一行是主題標籤：主要主題在前，有次要主題時接在後面，例如 `#模型發布與能力`。主題名稱裡不能出現在 Telegram hashtag 的字元一律換成底線。完成通知與更新通知都附主題。

### X 費用帳本

- X 讀取的結果分三種：
  - 收到非 2xx 的 HTTP 回應：預留結算為 0，狀態記為新的 `failed`。用量資料記下狀態碼、讀取類型（書籤、貼文、使用者等）與發生情境（書籤同步、分享收件、長文等）。
  - 沒有收到回應（逾時、連線錯誤）：記為 `uncertain`。
  - 收到 2xx 回應、但之後的處理失敗（例如內容過大或解析失敗）：也記為 `uncertain`，因為 X 可能已經計費。
- 新狀態 `voided` 表示作廢。月預算的已使用金額與預留檢查都排除 `voided`；`failed` 的金額固定為 0。
- 作廢 API：只能作廢 `uncertain` 的費用，必須附說明；記下作廢時間與說明，金額保留供對照。
- migration：既有 X 類（`x`、`x-reread-risk`）的 `uncertain` 費用全部改成 `voided`，說明寫「升級時作廢：X 失敗呼叫的預留或重讀風險估算」。其他類別的未確認費用不動。
- 停止記錄 `x-reread-risk`，移除相關部署變數。同一 UTC 日的首讀判斷（重讀不計費）維持不變。
- 預算區塊：
  - 「未確認」明細的每一筆都有作廢按鈕。
  - 新增「已作廢」合計，可展開看每筆的時間、類別、金額與說明。
  - 新增「X 失敗呼叫：本月 N 次，未計費」，附最近一次的狀態碼與情境，可展開看每次的時間、讀取類型與狀態碼。
- 人工調整 API 保留，不做表單。

### 暫停與恢復

- 「恢復處理」只在暫停中顯示，旁邊顯示暫停原因（手動或費用不足），並用一句話說明按下會做什麼。按下後的行為不變。
- 費用暫停、剩餘預算為 0 時，恢復會失敗並顯示「剩餘預算為 0，請先作廢未確認費用或調整月預算」。
- 作廢費用後，管理頁重新讀取預算與暫停狀態。不自動恢復，由使用者決定。

### 維護排程

- 維護排程保留：失敗工作重試、分類重試、通知補送、收件回覆補送、媒體過期、登入 session 清理、書籤同步續跑（啟用時），以及新增的來源條目與發現紀錄 30 天清理。

## Testing Decisions

- 好的測試只檢查使用者看得到的結果：管理頁與文章庫 API 的回應、送出的 Telegram 訊息、預算數字。不檢查內部函式或資料表的形狀。例外是 migration 本身就是行為的地方，例如既有未確認費用升級後變成作廢，也透過預算 API 驗證。
- 所有測試從 Worker 的入口進行：網站與 API（fetch）、排程（scheduled）、工作佇列（queue）。資料庫用記憶體 SQLite 套用全部 migration；Telegram 與 X 用記錄呼叫的假網路，可以模擬錯誤狀態碼與逾時；官方列表、原文、文字模型、分類器用注入的依賴；時間用注入的 `now()`。
- 要測的行為：
  - 官方發現與新鮮度：太舊略過、沒有日期時抓到原文後再判斷、以收件時間為準、分享與仍要收件不受限、新來源回補。
  - 官方來源 API：每列的數字、最近 7 天條目、30 天清理、仍在列表上的網址不被清除、開關、設定驗證失敗時原設定不變、仍要收件會整理並通知。
  - 失敗提醒：連續兩次失敗發一則；第三次不重發；成功後歸零，下次故障再提醒；空列表算失敗；關閉的來源不提醒。
  - 分類時機：Gemini 寫作與 Mac 執行器完成兩條路徑都會立刻分類，通知第一行附主題；分類失敗時通知照常、不附主題，之後由維護排程重試成功。
  - X 帳本：錯誤回應記 0 並出現在失敗呼叫明細；逾時記未確認；作廢後從預算排除並出現在已作廢明細；不再產生重讀風險；升級後既有的 X 未確認變成作廢。
  - 暫停與恢復：狀態 API 回傳暫停原因；管理頁腳本在暫停與未暫停時的按鈕顯示；預算為 0 時恢復失敗並回傳說明。
  - 舊流程移除：舊端點回 404；08:00 排程不再呼叫舊流程；舊版短導讀仍出現在列表、可以閱讀。
  - 維護排程：不再執行一次性搬移（插入一篇待搬移的舊導讀，維護後仍未搬移）；「維運」按鈕仍能搬移。
- 舊流程專屬的測試（digest 執行、四選一模型、導讀格式）隨程式一起移除；仍有價值的斷言（例如發現與新鮮度）改寫到文章庫的測試。
- Formatter 工作票：重排前後全部測試都通過，`format:check` 通過。
- 參考既有測試：官方發現與 Gemini 篩選（`official.test.js`）、預算與費用（`budget.test.js`）、通知（`notifications.test.js`）、主題與管理頁 API（`topics.test.js`）、管理頁腳本渲染（`library-ui.test.js`）、測試工具（`helpers.js`）。
