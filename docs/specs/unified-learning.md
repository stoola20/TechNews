# 統一詳細整理、本機文字模型與桌機文章庫

**Status:** ready-for-agent

**使用者：** 單一使用者，自用。需求討論已收斂；12 張 tickets 的粒度與阻擋關係已核准並發布。

## Problem Statement

官方文章、X 書籤與 Telegram 分享目前分別使用不同資料流程。官方文章只產生 Telegram 導讀，沒有進入收藏文章庫；收藏的媒體理解、教材寫作與追問都使用 Gemini。模型設定、任務狀態與閱讀入口缺乏一致性，難以判斷文章是否已取得、正在處理、等待重試或已完成。

官方文章與新書籤目前都由台灣時間 09:00 的日次排程啟動，不符合使用者希望官方文章在 08:00 開始整理、書籤更頻繁被發現的需求。每五分鐘的維護排程不會主動開始新一輪書籤同步。直接提高同步頻率，也會碰到現有費用帳本重複累計 X 讀取的問題。

使用者有常開、32 GB 記憶體的 Apple Silicon Mac mini，已使用 Apple container 與 Ollama 的 Gemma 26B。希望以此承擔文字整理，但不能犧牲完整度、技術正確性及來源可查核性，也不能把模型檔案大小當成執行記憶體或速度保證。

網站以桌機閱讀為主要情境。現有頁面把閱讀、收件、費用、授權與維運混在一起，返回導覽、處理狀態更新、失敗篩選、筆記保存及追問歷史都有改善需要。

## Solution

官方文章、X 書籤、Telegram 與網站分享都進入同一私人文章庫，共用來源身分、工作狀態、完整文章、搜尋、筆記、已讀與來源追問。所有正式新文章都詳細整理，依原文深度保留目的、背景、機制、推理、例子、操作、限制與取捨；官方文章也不能只留下短導讀。

雲端繼續保存網站、收件、排程、原文、媒體、工作、文章、筆記及通知狀態。Mac 主動領取文字工作，使用 macOS 原生 Ollama 執行 Gemma。Gemini Flash 先專責圖片與影片理解，將可查核的媒體證據保存後，連同原文送給 Gemma 寫作。單篇及跨篇追問也改由同一文字模型處理。正式切換前必須通過代表素材的品質與效能驗證。

台灣時間每天 08:00 開始官方來源整理。書籤每十分鐘做有限範圍的檢查，每天另做完整分頁核對；完整核對預設也在 08:00 啟動。兩者分開保存進度與覆蓋狀態，不承諾每筆新收藏都在十分鐘內發現。Telegram 與網站分享立即收件並排隊。

網站完成後立即可讀，所有入口的文章完成後即逐篇發 Telegram 通知，提供精簡介紹、必要缺漏提示與完整文章連結。相同內容不因重複收件再次生成或通知；補到新來源而產生實質內容更新時，更新同一篇並發更新通知。

桌機以文章列表與閱讀雙欄為中心，閱讀之外的管理操作集中到獨立入口。Mac 短暫不可用時保存工作並明示等待，恢復後續跑，不自動改用雲端文字模型。

## Implementation Decisions

### 共同資料與相容演進

- 以現有私人文章庫為整合基礎，建立共同來源身分、收件關係、證據、工作、媒體解析、文章版本、追問、閱讀與通知紀錄。先擴充相容資料及讀取能力，再逐條改接寫入流程，避免一次切斷既有服務。
- 正規化同一文章網址與 X post ID，保存官方、書籤、分享等多個收件關係。X 貼文及其外連文章是不同來源，不因存在連結就直接合併成同一文章身分。
- 同一來源的筆記、已讀狀態不隨重新整理或版本變更重設。文章舊版本保留，媒體觀察、正文與生成資訊可追溯到實際來源版本。
- 重複收件回覆既有文章入口；若尚在處理則回覆同一工作的狀態。不同入口不能各產生一份完成通知；新收件關係也不能使已通知版本重新成為待通知。
- 匯入已保存官方文章與收藏教材，重用既有原文、模型資訊及通知紀錄。只有短導讀的舊資料標為既有導讀，不能標成已完成新規格的詳細教材；有來源缺漏時如實顯示。搬移本身不觸發模型、外部來源讀取、回補或通知。
- 同一來源在舊兩套資料中都存在時合併收件與版本，保留既有收藏教材、筆記與已讀；若原有文章識別碼改變，舊深層連結仍須能導向合併後文章。
- 既有設定與登入可繼續使用；新增本機執行器憑證不輪替既有登入及 X 憑證加密所依賴的秘密。

### 排程與書籤覆蓋

- 所有使用者時間以 Asia/Taipei 呈現。官方來源每日 08:00 開始發現新文章及排入工作，不承諾 08:00 前完成。沿用既有來源設定與新來源回補規則，不擴成官方文件全站爬取。
- 官方發現工作與後續整理分開；受每次處理量限制而剩餘的文章，由背景工作持續消化，不必等到隔天的官方排程。
- 書籤每十分鐘從目前可取得列表的起始頁做局部檢查。預設上限一頁、最多一百筆，作為可調整的操作設定，不宣稱它是完整增量同步。
- 每日 08:00 另啟動完整核對，逐頁保存游標直到沒有下一頁。遇到已知 ID 或回傳不足一百筆都不能單獨作為全掃結束條件。分頁期間資料可能變動，完整掃描也不宣稱平台提供一致快照。
- 局部檢查與完整核對各有進度、鎖及時間紀錄，不能互相覆寫游標。同一範圍的重疊排程共用在途工作；局部檢查不能把完整核對標成成功。對來源 API 的呼叫集中協調，避免重複與超過限制。
- 首次基線仍以完整掃描及既有回補確認流程為準；基線未完成時局部檢查不得把尚無法可靠分類的舊收藏直接當新收藏處理。
- 顯示最後局部檢查、最後完整完成、正在掃描範圍、尚未完成及原因。新增收藏舊貼文可能直到每日全掃才被發現，這是選定的成本與完整度取捨。
- 授權錯誤、限流、游標失效及預算暫停保存可恢復狀態；不能悄悄降成日次檢查或宣稱沒有新收藏。
- 排程以明確任務分流，不再依賴單一舊 Cron 字串判定所有日次行為。官方排程、局部檢查、完整核對、維護與來源重查可分別驗證。

### 模型分工與媒體證據

- 目標文字模型為本機 Ollama Gemma 26B，負責官方主題判斷、詳細整理、通知介紹及單篇／跨篇來源追問。每次保存實際 provider、model、模型／提示版本與輸入指紋，不把本機 Gemma 與 Workers AI 同名模型當成等價部署。
- Gemini Flash 先負責既有範圍的圖片與影片理解。第一版不把圖片再搬到本機，也不新增專用 OCR、語音、embedding 或其他模型服務。
- 媒體階段輸出獨立且可驗證的證據契約：來源與素材身分、原文 OCR 或可辨識語音文字、畫面觀察、影片時間點、觀察與推論的區分、未辨識與覆蓋缺口、實際解析模型及版本。沒有可辨識文字或語音時明確記錄，不要求模型填造逐字稿。
- 影片語音、畫面分別記錄可取得的內容及涵蓋範圍；不能因為有一個時間點觀察，就宣稱完整理解整段影片。來源時間點須合法且不超過片長，引用必須對應實際素材。
- Gemini 先保存媒體解析，再由 Gemma 接收原文及有效解析，產生詳細正文與通知介紹。媒體來源內容當作資料，不能作為指示執行系統操作或取得秘密。
- 媒體解析與文字寫作分別 checkpoint，以素材內容／版本、解析模型、提示與證據版本建立重用依據。媒體解析有效時，文字失敗或手動重寫不再次呼叫 Flash。
- 保留既有主文、父貼文／引用、作者補充及直接外連證據的取得能力。官方自動來源第一版維持全文文字；主動分享沿用現有可取得圖片及 X 影片範圍，不新增任意網站影片抓取。
- 沿用單支影片二十分鐘、單媒體二百 MB 及原始媒體三十天保存政策。超限、過期及不可取得素材明示缺漏；不以縮圖代替影片，也不默默裁短。
- 所有新正式文章包含詳細正文、通知介紹、引用、缺漏及模型資訊。Telegram 字數限制只約束通知，不裁切詳細正文。官方來源仍套用主題篩選，主動分享與收藏不以低相關性淘汰。
- 不為了塞入本機 context 默默截掉來源尾端。先保存完整來源；若無法在已驗證的處理範圍內完成，保留待處理及明確原因。第一版不以尚未驗證的長文分段策略宣稱已完整處理。

### Mac 執行器與持續工作

- 雲端 D1／R2 保存正式資料與工作，Mac 主動以驗證過的 API 領取、續約與回報文字工作；不對外暴露 Ollama、不要求手機連回家中，也不把 Mac 本機暫存當唯一資料來源。
- Ollama 在 macOS 原生執行，使用支援的 Apple GPU 後端。Apple container 可承擔背景執行器及隔離的非 GPU 工作，不把 Linux 容器 GPU 透傳當成已具備能力，也不為此新增 PostgreSQL。
- 提供常駐執行器的啟停、自動啟動、健康檢查與復原說明。設定限制推論並行度為一，設定經實測的 context／輸出上限；避免和其他容器同時消耗記憶體造成失控。
- 工作有持續保存的階段、嘗試、lease、attempt token、輸入版本及輸出版本。回報必須符合目前有效領取身分與輸入版本；過期或舊輸入的結果不能覆寫新文章。長工作以 heartbeat 續約。
- 網站顯示最後心跳、等待本機、排隊、取得來源、解析媒體、文字生成、完成、部分完成、可重試錯誤、需人工處理與費用暫停。Mac 不在線不是內容處理失敗，不消耗無意義的模型重試次數。
- 執行器重啟或網路恢復後接續工作；通知成功與內容生成分開保存，避免因回報或通知錯誤重跑有效階段。不聲稱跨外部 API 的 exactly-once。
- 排隊以來源追問優先，再手動分享，再例行官方／新書籤，舊回補最後；既有執行中的推論不強制中斷。加入避免背景工作永久飢餓的公平排隊規則。
- Mac 離線時網站仍可收件、閱讀及保存筆記；新文字工作等待恢復。正式切換後不自動 fallback 到付費或 Workers AI 文字模型。切換前保留現有路徑供比較，未通過驗收不啟用新預設。

### 追問與閱讀體驗

- 沿用現有原生 HTML、CSS、JavaScript，先改善資訊架構與互動；不為本次需求遷移前端框架。桌機文章列表／閱讀雙欄，窄螢幕切成清楚的列表及閱讀檢視。
- 首頁以文章庫與閱讀為主。收件入口保持容易找到；同步、來源、模型分工、預算與故障操作放管理入口，兩者有一致導覽及登入體驗。
- 搜尋涵蓋標題、詳細正文與已保存來源，提供未讀、來源類型／收件入口與處理狀態篩選。搜尋、篩選、分頁及目前文章與 URL／瀏覽歷史一致，返回後保留列表位置。
- 保留手動已讀／未讀。筆記自動保存並顯示保存中、已保存及失敗狀態；切換文章與狀態刷新不能覆蓋未保存草稿，舊請求回應不能寫入另一篇文章。失敗草稿保留可重試，跨分頁衝突不能靜默覆寫。
- 進度更新涵蓋所有收件入口與追問，而非只在書籤同步中才更新。刷新處理狀態不能重建正文或筆記輸入而遺失使用者操作。
- 「需要處理」是可操作狀態集合，涵蓋錯誤、缺漏、需重新授權等情況；等待本機與費用暫停另有明確標示及篩選，避免把正常等待當失敗。
- 分開提供補取缺漏、重寫文字與重送通知等動作，執行前說明涉及的來源取得或模型階段。新素材重新解析才會重新支付媒體費；不能所有重試都從頭開始。
- 閱讀頁提供保存原文、來源片段、媒體與時間點，清楚區分來源內容、模型觀察、額外教學例子與缺漏。媒體尚在保存期時可用時間點回看，過期後保留觀察與原始連結。
- 單篇及跨篇追問沿用 D1 關鍵字檢索，不新增向量服務或串接選用 Python RAG。來源片段與媒體觀察都有穩定引用身分；只有實際提供的證據才能被引用，資料不足時明說無法確認。
- 追問改為可持續保存的非同步工作，回覆工作身分與進度；完成後可在網站查看歷史，不依賴長時間持續開啟的 HTTP 連線。追問不自動產生新的 Telegram 文章完成通知。
- 桌機與手機都保留鍵盤操作、可見 focus、具標籤控制項、載入／錯誤回饋、足夠對比、可讀行長、程式碼與表格滾動及 reduced-motion。介面顯示實際模型分工，不能仍讓人以為設定頁模型只控制其中一條流程卻套用全部。

### 通知、重複與更新

- Telegram 分享立即回覆已保存，完成後逐篇通知。官方、書籤及網站分享也都在詳細文章持續保存後即安排完成通知，不再日次／半小時集中。
- 通知使用精簡介紹、文章連結及必要缺漏提示；不把精簡介紹當文章全文。沒有新完成或新更新就不發空通知。
- 完成通知依共同文章身分與內容版本去重，入口不同不產生多份完成通知。使用者再次分享已完成連結可收到既有文章入口，與全域完成通知分開處理。
- 保留現有 X 作者補充二十四小時後重查一次的行為。來源沒有實際變動就重用結果；真正新增補充或修復缺漏時更新同一文章、保留舊版，發明確的更新通知。僅模型 metadata、搬移或等價格式變動不算內容更新。
- 通知內容與發送狀態持續保存，重送不重抓來源或重生成。外部發送成功但回應／存檔失敗仍可能少量重複，不能宣稱絕對只送一次。

### 費用與暫停

- 統一流程先採每台灣曆月 US$30 的雲端預算，納入 X、Gemini、相關儲存與適用的雲端基本／用量費。Mac 電費另計，舊帳目不因資料搬移再次計入。
- 沿用付費呼叫前原子預留、成功後結算、未知計費失敗保留風險的原則；顯示估算、預留、未確認與可核對用量，不把內部帳本當供應商帳單。
- 修正 X 日內重讀帳本：依供應商查核過的計費範圍、UTC 日與資源身分區分首次讀取及可能去重的重讀。台灣曆月預算和供應商 UTC 日重設分開處理。
- 官方日內去重是 soft guarantee，不能將重讀風險直接歸零；保留可設定的保守重讀風險額度與未確認成本，並能與供應商用量核對、修正。正常去重估算也不能把每十分鐘返回的所有舊資源都當成已確認新費用。
- Owned Read 優惠只在確認帳戶及 app 條件符合時使用，否則採一般費率。單價與政策保留查核日期及設定，不因模型或 API 名稱相同就套用舊價格。
- 達門檻停止新付費來源讀取、媒體解析及付費重試，仍收件並保留工作；已有完整證據的本機文字工作、網站閱讀、筆記與重送既有通知可繼續。管理員手動暫停全部處理與費用暫停必須明確區分。
- 費用暫停跨月不自動恢復，手動恢復仍檢查可用預算。來源或媒體階段無法取得時，不用虛構來源讓本機工作假裝完整。

## Testing Decisions

- 主要整合邊界為「收件／排程 → 真實 schema 與 migration → 持續工作 → 媒體證據 → Mac 領取回報 → 文章／追問讀取 → Telegram」。測外部可見狀態、保存內容與副作用，不以私有 helper 的呼叫數或實作形狀作為驗收。
- 優先延伸現有 Worker pipeline 與 learning handler 測試：真實 SQLite schema、可替換外部網路與時間、模擬 Queue／R2。Mac 協定透過公開領取／續約／回報 API 驗證；Ollama、Gemini、X 與 Telegram 只保留必要的供應商契約測試。
- 排程驗證 08:00 官方開始、十分鐘局部檢查、每日全掃、來源重查及維護互不誤觸，並驗台灣／UTC 邊界、排程重複與在途工作重用。官方積壓可於背景續跑。
- 書籤驗證局部頁數限制、每日完整分頁、舊 ID 不截斷全掃、短頁仍有 next token、局部不宣稱完整、基線與回補、游標失效、限流、授權與費用中斷。舊貼文新收藏的延遲必須符合選定的局部掃描語意。
- 共同資料驗證跨入口去重、同一網址多關係、不同 X／外連文章不誤合併、舊深層連結、搬移冪等、通知版本不重送、筆記／已讀保留、舊短導讀及缺失模型資訊不冒充新產物。搬移測試不得觸發外部 API。
- 媒體驗證 OCR／可辨識語音／畫面證據與缺口、時間點範圍、來源身分、拒絕捏造引用、解析快取重用、媒體到期、超限及純文字路徑不呼叫媒體模型。文字失敗不能使有效媒體解析消失。
- Mac 驗證身分與任務權限、單工、續約、斷線與重啟、lease 過期後重新領取、過期結果及舊輸入回報被拒絕、回報重播冪等、優先順序與背景公平性。Mac 離線不增加錯誤次數，也不觸發雲端 fallback。
- 文章驗證官方與收藏都產生詳細正文、不受通知篇幅限制、來源尾端與限制未被靜默丟棄、官方主題篩選不套在主動收藏、模型未完成時不標完成。作者無變更不重寫，有實質新內容才更新版本與通知。
- 追問驗證非同步接受、等待本機、完成與歷史、單篇／跨篇範圍、引用片段及媒體來源、不足回答；重開頁面可讀進度，追問不發文章完成通知。
- 費用驗證原子預留、確定／未知結算、X UTC 日重讀及台灣月切換、優惠資格、保守風險設定、預算不足不新付費、暫停後仍本機處理已取得證據、手動恢復及跨月不自動解除。
- UI 沿用既有 Markdown 安全渲染回歸，另以瀏覽器操作驗證桌機雙欄、手機閱讀、篩選與返回位置、深層連結、所有入口進度更新、筆記切換／網路失敗／舊回應衝突、追問歷史、鍵盤及窄螢幕溢位。不能只檢查 HTML 字串就宣稱互動已驗收。
- 正式切換前至少十二組代表素材對照原有結果與新流程，涵蓋官方長文／程式碼、文字討論串、圖片、影片、缺漏、單篇及跨篇追問。逐項核對來源與完整度；重大事實錯誤、捏造引用及未標示來源缺漏不得通過。補充教學必須有明確標記。
- 本機實測記錄冷啟動、暖機、輸入／輸出長度、完成與排隊時間、峰值記憶體、記憶體壓力及 Apple container 共存情境。至少一次驗證中斷復原與積壓工作，不把模型磁碟大小當執行 RAM。以量測結果訂運行設定與揭露支援範圍，先不承諾未實測的秒數。
- 品質未通過時保留現有正式流程，調整後重新驗收；程式模擬、供應商契約、本機模型、真實來源及 UI 操作的證據分開記錄，未測事項明列未完成。

## Out of Scope

- 多使用者、公開文章分享、團隊權限、付費訂閱或原生 App。
- 官方文件全站爬取、任意網站影片下載、全網遞迴取材、監看所有 X 留言。
- 官方自動來源的圖片／影片理解擴充；本版維持既有全文文字範圍。
- 新增第三個模型、embedding、向量資料庫，或把獨立 Python RAG 併入正式流程。
- 第一版以本機模型處理圖片或影片、容器 GPU 透傳、搬移整個網站及正式資料到 Mac。
- 前端框架遷移、收藏夾、標籤管理、稍後讀與封存等未確認的閱讀功能。
- 自動重新生成全部舊文章、重新下載全部媒體、啟動所有舊收藏回補或重送歷史通知。
- 保證每筆書籤十分鐘內被發現、保證來源平台全歷史可取得，或保證 Telegram 絕對不重複。
- 未驗證的長文截斷／分段摘要、無限制 context、未量測的本機 SLA，以及失敗後自動改用另一個文字模型。
