# 文章庫依發表時間排序、主題分類與列表改版

**Status:** ready-for-agent

**使用者：** 單一使用者，自用。需求已逐題確認；列表設計稿選定 B（[`docs/previews/library-list-b.html`](../previews/library-list-b.html)）。tickets 依本規格拆分後直接開發。

## Problem Statement

文章庫列表難以找到內容，主要有三個原因。

1. **排序依據不是原文時間。** 列表依「加入文章庫的時間」排序。技術推進很快，使用者判斷一篇文章是否過時，靠的是原文發表時間。一次回補的舊書籤，原文可能橫跨數個月，卻全部擠在回補當天；官方文章隔天才整理，也排在前一天分享的貼文後面。
2. **發表時間資料不一致。** 原文發表時間只存在來源資料中，格式混雜：RFC 2822（`Fri, 16 Oct 2026 00:00:00 GMT`）、含時區縮寫（`PDT`）、ISO 8601、只有日期。直接比較字串無法排序。搬移進來的舊官方導讀沒有在來源中保存發表時間，雖然部分日期還留在舊的官方文章表與收件紀錄裡。
3. **列表標籤是管理資訊，不能幫忙找文章。** 每篇文章顯示處理狀態、收件入口（官方來源、X 書籤、Telegram 分享…）與「既有導讀」。這些用於維運，不能回答「這篇講什麼主題」。文章庫沒有任何主題資料。

另外，X 書籤同步與作者重查的開關目前寫死在部署設定。使用者想停用書籤同步以節省 X 讀取費用，也希望之後能在管理頁自行切換，不必重新部署。

## Solution

列表預設依原文發表時間由新到舊排列，並依發表日分組。使用者可以切換成依加入時間排序，用來找剛分享的文章。發表時間在保存來源時統一轉成 UTC ISO 格式，記在文章上；舊導讀的日期從既有資料補回。仍然查不到日期的文章，用加入時間代替，並明確標示「日期未知」。

文章依一份固定主題表分類：每篇 1 個主要主題，最多 1 個次要主題。分類是獨立步驟，由 Workers AI Gemma 4 讀標題與導讀後，從主題表中選擇；不依賴哪個模型寫教材，也不經過 Mac。新文章完成或內容更新後自動分類，既有文章由同一機制回補。閱讀頁可以手動改主題，手動結果不會被模型覆寫。主題表在管理頁維護。

列表採設計稿 B 的緊湊清單：搜尋、未讀、排序、管理篩選與主題 chip 固定在頂端。每篇顯示主題顏色點、最多兩行的標題，以及「主題・發布者・日期」。處理狀態只在未完成或有問題時顯示。收件入口與「既有導讀」移到閱讀頁。捲到底自動載入更多。

X 書籤同步與作者重查改成管理頁上的兩個開關，保存在資料庫。沒有設定時兩者都關閉。

## Implementation Decisions

### 原文發表時間

- 文章新增可為空的「原文發表時間」欄位，保存 UTC ISO 8601。保存主要來源（primary）時，解析來源的發表時間並寫入文章；無法解析時保持空值，不猜測。
- 解析器接受 RFC 2822（含 `GMT`、數字時差與常見美國時區縮寫，例如 `PST`／`PDT`）、ISO 8601 與只有日期的 `YYYY-MM-DD`。只有日期時視為該日 00:00 UTC。
- 回補在維護排程中執行，冪等。依序嘗試：文章的主要來源、收件紀錄 metadata 中的發表時間、舊官方文章表中對應網址的發表時間。
- 列表排序鍵：`published`（預設）使用「發表時間，沒有時用加入時間」，`added` 使用加入時間；兩者都以文章 ID 作為次要排序，確保分頁穩定。
- 列表 API 新增 `sort` 參數（`published`｜`added`），回傳每篇的發表時間與加入時間。日期分組與「日期未知」標示由前端依台灣時間計算。

### 主題表與分類

- 主題表存在 settings，每個主題有固定識別碼（英數小寫與連字號）、名稱、給分類模型參考的說明，以及顏色。初版 7 個主題：

  | 識別碼 | 名稱 |
  | --- | --- |
  | `models` | 模型發布與能力 |
  | `ai-coding` | AI Coding 工具 |
  | `agent-engineering` | Agent 架構與工程實踐 |
  | `product-updates` | 產品功能更新 |
  | `apple` | iOS／Apple 開發 |
  | `safety-policy` | 安全、治理與政策 |
  | `enterprise` | 企業導入案例 |

- 文章新增欄位：主要主題、次要主題、分類來源（`model`｜`manual`）、分類時對應的文章 revision、分類失敗次數與下次重試時間。
- 分類條件：狀態為已完成或部分完成、分類來源不是 `manual`，且尚未分類、分類時的 revision 小於目前 revision，或主要主題已不在主題表中。
- 分類在每 5 分鐘的維護排程執行，每輪處理有限篇數（例如 10 篇），依加入時間新到舊，讓新文章先分類，舊文章逐輪回補。新文章因此在完成後數分鐘內就有主題，不另外排工作。
- 分類模型為 Workers AI `@cf/google/gemma-4-26b-a4b-it`，使用既有的 AI binding。輸入為主題表（識別碼、名稱、說明）與文章標題、導讀；沒有導讀時用正文前段。輸出 JSON `{primary, secondary}`，程式驗證兩者都屬於主題表、次要主題可為空且不同於主要主題。驗證失敗或呼叫失敗時累計失敗次數並延後重試；連續失敗後停留在「未分類」，不影響文章其他功能。
- 分類不記入月預算（Workers AI 使用免費額度），也不觸發 Telegram 通知。
- 手動設定：閱讀頁可選擇主要與次要主題，保存後分類來源改為 `manual`。提供「改回自動分類」，清除手動標記，讓下一輪維護重新分類。
- 主題表修改：
  - 改名或修改說明、顏色：識別碼不變，文章不受影響。
  - 刪除主題：主要主題被刪的文章清除主題並回到待分類，手動標記也一併清除。只有次要主題被刪的文章則移除次要主題，其他不變。
  - 新增主題：不自動重分。管理頁的「重新分類全部」會讓所有非手動文章回到待分類。
  - 至少保留 1 個主題；名稱不可重複；識別碼建立後不可修改。
- API：
  - `GET topics`：回傳主題表與各主題篇數。篇數依目前非主題篩選條件計算，同時計入主要與次要主題，並附「未分類」篇數。
  - `GET items` 新增 `topic` 參數：主題識別碼或 `unclassified`。篩選同時比對主要與次要主題。
  - `PUT items/:id/topics`：手動設定或清除手動設定。
  - `PUT admin/topics`：取代主題表，並依上述規則處理受影響文章。
  - `POST admin/topics/reclassify`：重新分類全部非手動文章。

### 列表與閱讀頁（設計稿 B）

- 列表頂端固定：搜尋列；「只看未讀」、排序下拉（發表時間／加入時間）、「管理篩選」按鈕；主題 chip 列（全部、各主題、未分類，附篇數，單選，橫向捲動）。
- 「管理篩選」展開後顯示既有的收件入口與處理狀態篩選；任一管理篩選生效時，按鈕顯示啟用狀態。
- 日期分組標題為「M 月 D 日（週X）」，跨年時加上年份，右側顯示該組篇數。分組跟隨目前排序鍵。
- 每篇：主題顏色點；標題最多兩行，未讀粗體、已讀細字；meta 列為「主要主題（、次要主題）・發布者・日期」。沒有發表時間時日期顯示「日期未知・加入於 M/D」。處理狀態只在非已完成時附在 meta 後面（部分完成也算有問題），沿用既有狀態文字。
- 發布者：官方收件使用來源設定名稱；X 文章使用作者帳號 `@username`；其他使用網址網域。由列表 API 一併回傳。
- 載入更多：保留每批 50 篇的 offset 分頁，捲到底時用 IntersectionObserver 載入下一批並接在後面；同時保留一個「載入更多」按鈕作為無法自動觸發時的備援。篩選或排序改變時從第一批重新載入。網址不再保存頁碼。
- 閱讀頁文章資訊：主題（含手動修改入口）、發布者、發表時間、加入時間、收件入口、「既有導讀」標示。
- 不保留舊列表的狀態徽章、收件入口徽章與上一頁／下一頁按鈕。

### X 讀取開關

- 書籤同步與作者重查各自保存在 settings，預設都關閉，移除部署設定中的環境變數。
- 書籤同步關閉時：每 10 分鐘局部檢查、每日完整核對、續跑、手動「同步書籤」、X 授權回呼都不讀 X 書籤。已保存的待回補書籤仍可逐篇整理。
- 作者重查關閉時：完成 24 小時後不重查作者補充。
- 手動分享 X 連結不受兩個開關影響。
- 管理頁在 X 同步區塊顯示兩個開關，切換後立即生效，並顯示目前狀態。狀態 API 回傳兩個開關的值。

### 流程與公開 repo

- 本 repo 公開。commit、PR、測試與文件只放通用需求與合成資料，不寫入私人文章標題、網址、帳號或操作紀錄。

## Testing Decisions

- 好的測試只驗證外部行為：透過 Worker 的 HTTP handler 與 scheduled／service 介面操作，用真實 SQLite schema（依序套用全部 migration）與合成資料，不斷言內部函式呼叫順序。
- 測試縫隙沿用既有最高層：`createLearningHandler` 的 `fetch`、`service.scheduled`，以及頁面腳本可被解析的檢查。Workers AI 以測試環境的 AI binding 替身注入，記錄呼叫並回傳合成 JSON。
- 發表時間：各種格式都能解析；無法解析時為空值；回補依序使用三種資料；`sort=published` 與 `sort=added` 的順序正確，日期未知的文章依加入時間排入。前例：`library-ui.test.js` 的列表篩選測試。
- 分類：維護排程只分類符合條件的文章，每輪有篇數上限；模型回傳不在主題表中的識別碼時視為失敗並延後重試；revision 增加後重新分類；手動設定不被覆寫；改回自動後重新分類；主題刪除、改名、重新分類全部的影響範圍正確。前例：`official.test.js`、`bookmark-sync.test.js` 的排程測試。
- 列表 API：`topic` 篩選比對主要與次要主題，可與搜尋、未讀、收件入口並用；`GET topics` 的篇數正確，包含未分類；發布者欄位依收件類型正確。
- X 讀取開關：沒有設定時兩者關閉，排程、續跑、手動同步、授權回呼都不呼叫 X；開啟後恢復既有行為；手動分享不受影響。前例：`bookmark-sync.test.js` 的停用測試。
- UI：頁面與管理頁腳本可解析；以內建瀏覽器在桌機與手機寬度實際操作排序、主題 chip、管理篩選、載入更多與閱讀頁手動改主題，並確認手機寬度沒有橫向捲動。

## Out of Scope

- 發布者篩選（只顯示）。
- 模型自由產生的關鍵字標籤。
- Telegram 通知附上主題。
- 依主題的相似文章推薦、語意搜尋。
- 重抓原文來補齊查不到的發表時間。
- 部署與正式環境 migration；完成後另行決定。

## Further Notes

- 分類只讀標題與導讀，是為了把每篇的輸入控制在數百字內，讓回補在免費額度內完成；之後若準確度不足，再考慮加入正文前段。
- 主題篇數會隨主題篩選以外的條件（搜尋、未讀、管理篩選）變化，讓 chip 上的數字和點下去看到的篇數一致。
