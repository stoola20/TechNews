## A 結論：分開處理階段，不必綁定兩家模型

```callout ok 對你的需求，我會先比較兩條路
先用 Gemini 單獨解析與寫作，建立品質基準。
再比較 Gemini 解析＋Claude 寫作。
只有 Claude 的教材品質確實較好，才保留雙模型。
先前的配置是候選分工，不是已驗證的最佳組合。
```

Gemini 能解析影片，也能編寫教材。
Claude 並非必需的第二個模型。
值得保留的是原始證據與處理階段的邊界。
兩個階段可以使用同一模型，也可以各自更換。

## B 如果分工，兩個模型各自收到什麼？

```flow TB
(X 原文與作者補充) -> [(來源證據庫)]
(取得的影片) -> Gemini 影片解析
Gemini 影片解析 -> 逐字稿與時間點觀察
逐字稿與時間點觀察 -> [(來源證據庫)]
(關鍵畫面) -> [(來源證據庫)]
來源證據庫 -> 教材寫作: Gemini 或 Claude
教材寫作 -> 完整繁中文章與引用
```

**解析階段**：辨認說了什麼、畫面顯示什麼。
保存時間點、逐字稿、畫面觀察與不確定處。
不要只輸出一段短摘要。

**寫作階段**：結合原文、補充與媒體證據。
解釋背景、機制、操作、例子與限制。
Claude 若需要查核畫面，可直接接收關鍵圖片。
Claude 的圖片介面支援多張圖片與文字。
時間點需由我們明確提供。
[Claude 圖片文件](https://platform.claude.com/docs/en/build-with-claude/vision)

沒有影片的文章可以直接進入寫作階段。
不需要每篇都呼叫兩個模型。

## C 分成兩個模型，實際得到什麼？

| 面向 | 潛在好處 | 代價與邊界 |
|---|---|---|
| 品質調整 | 可分別選影片解析與教材寫作模型 | 目前沒有實測證明 Claude 寫作更好 |
| 重寫文章 | 沿用已保存的證據，調整篇幅與結構 | 同一模型分兩階段，也能做到 |
| 排查錯誤 | 能分清楚解析錯誤與寫作錯誤 | 需保存完整輸入與處理結果 |
| 模型替換 | 可只更換寫作模型或解析模型 | 需維護兩家 API 與失敗處理 |
| 成本與等待 | 避免每次重寫都重新解析影片 | 串接兩次仍會增加費用與等待 |
| 資料處理 | 可指定各服務收到的資料 | 使用兩家供應商，資料會送往兩個服務 |

**最重要的風險是資訊交接時被壓縮。**
若 Gemini 漏掉一個設定，Claude 不會自動知道。
第二個模型讀第一個模型的結果，不算獨立查核。
保留原文、關鍵圖片與時間點，才能回頭驗證。

## D 除了 Gemini，還有哪些理解影片的方式？

| 方式 | 理解哪些內容？ | 優點 | 主要限制 |
|---|---|---|---|
| Gemini 原生影片輸入 | 影片畫面、音訊與時間關係 | 可直接問片段與時間點 | 仍需取得 X 媒體；取樣可能漏細節 |
| Grok＋X Search 影片工具 | 搜尋取得的 X 貼文影片 | 與 X 取得流程整合 | 不保證取得指定影片或完整討論串 |
| 音訊轉錄＋抽畫面＋Claude | 逐字稿與附時間點的圖片序列 | 取樣與保存可控，Mac mini 可前處理 | 畫面間的動作可能漏失；音畫需對齊 |
| 本機 Qwen 視覺模型 | 影片取樣畫面與文字 | 可本機部署與自訂處理 | 模型、量化與執行環境需測；音訊另安排 |
| NotebookLM | YouTube 逐字稿、文件與匯入圖片 | 適合依來源學習與追問 | YouTube 匯入不分析原始影片畫面 |

Gemini 預設靜態處理取樣為 1 FPS。
3.8 Flash 也支援 agentic 模式，按需求探索片段。
能調整取樣不代表一定看見所有操作。
[Gemini 影片文件](https://ai.google.dev/gemini-api/docs/video-understanding)

Grok 的 X Search 可開啟影片理解。
這是 API 工具能力，和公開標記 @bot 的入口不同。
不能把它視為私人書籤同步介面。
[Grok X Search](https://docs.x.ai/developers/tools/x-search)

Qwen3.5-9B 官方模型卡提供影片輸入範例。
它是本機候選，不代表已在 M6／32 GB 實測可用。
[Qwen 官方模型卡](https://huggingface.co/Qwen/Qwen3.5-9B)

## E NotebookLM 能取代影片解析嗎？

**如果重點在講者說的內容，可以處理很大一部分。**
例如演講或 Podcast，可用逐字稿整理主張與追問。
但操作示範常有旁白未說出的畫面細節。

官方文件明列：YouTube 來源匯入的是逐字稿。
一般網頁來源也不匯入內嵌影片。
本機音訊來源會轉錄成文字。
即使音訊格式清單包含 MP4，也不代表分析影片畫面。
[NotebookLM 來源說明](https://support.google.com/gemininotebook/answer/16215270?hl=en)

可以先解析影片，再把逐字稿與圖片整理成學習資料。
NotebookLM 支援圖片與文件來源。
它能成為後續閱讀與追問介面。
但不應期待它自行從 X 網頁還原整段示範。

整合自建流程時，也要區分產品介面與模型 API。
Enterprise 有官方來源管理 API，需另評估方案與權限。
不能直接把一般 App 當成可替換的 Gemini API。
[Enterprise 來源 API](https://docs.cloud.google.com/gemini/enterprise/notebooklm-enterprise/docs/api-notebooks-sources)

## F 用一段示範看出逐字稿與影片的差別

**以下是教學假設，並非實測影片。**
講者說：「把這個選項打開，就能使用背景執行。」

| 證據 | 實際內容 | 教材需要保留什麼？ |
|---|---|---|
| 逐字稿 | 「把這個選項打開」 | 功能目的；仍缺選項名稱 |
| 00:18 畫面 | 使用者開啟某個 checkbox | 選項名稱與所在位置 |
| 00:21 畫面 | 畫面出現某個命令參數 | 操作步驟與參數拼字 |
| 作者後續回覆 | 僅限特定版本，另有例外 | 適用條件與限制 |

NotebookLM 若只取得字幕，可能知道功能目的。
但它沒有上述兩個畫面的直接證據。
影片模型或抽畫面流程，才有機會補齊這些資訊。
作者回覆仍須另外取得，影片解析無法補回。

若採抽畫面，先取場景切換與操作前後畫面。
看到「這個選項」等含糊旁白，再補取附近畫面。
關鍵命令與數字要檢查原圖，不能只信解析文字。

## G 我會怎麼調整方案 ②？

**架構保留取得、證據保存、媒體解析與教材寫作。**
模型配置保持可替換。

| 情境 | 起始處理方式 | 要驗證的問題 |
|---|---|---|
| 純文字與外部文章 | Gemini 或 Claude 直接寫作 | 哪個模型更忠於來源、解釋更完整？ |
| 操作示範影片 | Gemini 原生解析與寫作 | 是否保留畫面步驟與作者限制？ |
| 同一段影片的寫作比較 | 固定證據，Gemini 與 Claude 各寫一篇 | 第二個模型是否帶來實際改善？ |
| X 影片取得困難 | Grok X Search 作比較管道 | 能否取得目標影片與足夠可查核證據？ |
| Mac mini 到貨後 | 轉錄音訊＋取畫面，再交給視覺模型 | 是否比原生影片解析漏得更多？ |
| 想深入學習與追問 | 把整理好的來源加入 NotebookLM | 學習體驗是否足以省下自建介面？ |

比較時先固定證據，才能評估寫作差異。
另外比較解析結果，才能評估影片理解差異。
不要把「解析漏資料」誤判成「中文寫作不好」。
也不要因為兩個模型都寫出同一主張，就當作證實。

**目前推薦**：Gemini 單模型與雙模型並列實驗。
NotebookLM 作學習介面候選，不取代完整媒體取得。
是否保留 Claude，以實際文章品質決定。
